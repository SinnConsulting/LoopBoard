# Decisions — Loops & terminals

One line each: what, why. Newest at the bottom. Index: [../DECISIONS.md](../DECISIONS.md).

- `loopBoard.autoRecycle` defaults to **off** (user preference): auto-disposing a model's terminal when its task leaves In Progress kills the session mid-flow more often than it helps; ♻ is the manual, deliberate restart.
- Loop start passes the /loop prompt as the claude CLI's initial prompt argument (`claude --model X --permission-mode Y '<prompt>'`, single-quoted with `'\\''` escaping) instead of injecting the prompt text into the running TUI — injecting the multi-line prompt via sendText/sendSequence was unfixably flaky (bracketed paste swallows the newline; Enters within the TUI's paste-detection window get folded into the paste; sendSequence races terminal focus). The arg approach reliably delivers the prompt as argv, but the CLI only *seeds* it into the REPL input (a pasted-text chip) — it does NOT auto-submit. So after launch we send one standalone Enter (`terminal.sendText('', true)`) after `SUBMIT_DELAY_MS` (3.5s), once the CLI has booted and its paste-detection window has closed; a lone Enter after that window is not folded into the paste. `loopBoard.startupDelayMs` stays removed (the delay is now a fixed internal constant, not the old inject-the-prompt delay); ♻ restart re-arms the loop automatically.
- Loop terminals get a tiny bootstrap paste, not the full prompt (t-1d91): `buildLoopCommand` now emits `/loop <interval> You are running as model <model>. Open TODO.md, read the loop worker instructions in its ## Automation section, and follow them exactly...` — the Automation fenced block holds the standing model-agnostic instructions, so editing TODO.md retunes running loops on their next pass (only the interval is fixed at spawn). Chosen over startup validation (shell-integration exit-code checks only catch fast failures; tmux stays the v2 path — user decision: no follow-up story). Review feedback reversed the delivery mechanism to the ONE-command argv form (`claude --permission-mode <mode> --model <model> '/loop ...'` + lone Enter after boot to submit the seeded chip): with the bootstrap prompt this short, the quoting hazards that killed the argv approach for the 3,000-char prompt no longer apply.
- Models are configurable (t-c1a7, absorbed t-e4d2): the LOGICAL slot set stays fixed — `opus`/`sonnet`/`fable` plus new **`haiku`** — sourced from one place (`model.ts` `BUILTIN_MODELS`/`BUILTIN_MODEL_IDS`, which `parser.ts`/`merge.ts`/`terminals.ts` import so the allowlists can't drift). What each slot spawns as `claude --model <string>` is resolved from the `loopBoard.models` setting: per slot, `enabled` (false hides it from the Loops overview + board selects) and `model` (a custom `--model` string that REPLACES the default when non-empty — this is how you get `opus[1m]` for the 1M window, or an org alias). Chosen REPLACE-per-slot over a free-form user-defined list (user decision) — keeps `Model` a 4-value union and TODO.md `model:`/`groomer:` values a closed set, so no parser widening. Security: every resolved `--model` string is re-validated with a strict char allowlist (`[A-Za-z0-9._\[\]-]+`, admits `[1m]`) in `terminals.spawn()` before it reaches the shell line; an invalid override falls back to the built-in default and a disabled/invalid slot never spawns. The bootstrap prompt still names the logical slot (so a worker claims `model: opus` tasks) while the terminal launches with the resolved string. Webview selects are data-driven from `WebBoard.models` (enabled ids) + `defaultModel`, replacing the three hardcoded `['default (opus)', 'opus', 'sonnet', 'fable']` lists. Settings surface is VSCode's native `configuration` contribution (per-slot `{enabled, model}` object) — zero new webview, zero deps.
- `loopBoard.models` accepts a per-slot STRING shorthand in addition to the object form (t-c1a7 review feedback): `"haiku": "haiku[1m]"` is sugar for `"haiku": { "model": "haiku[1m]" }` (the common case — just overriding `--model`); the object form is only needed for `enabled: false`. `resolveModels` normalizes a string entry to `{ model }` via `asConfigObject`; the settings schema uses `anyOf: [string, object]` per slot. Users reached for the string form intuitively, so silently ignoring it was a footgun.
- Loop-row reveal desync fixed (t-2e35): `TerminalManager` (`src/terminals.ts`) now clears its cached `revealedModel` flag from a new `vscode.window.onDidChangeActiveTerminal` subscription whenever the active terminal is no longer the one last revealed — so hiding the panel externally (e.g. native CMD+J Toggle Panel, which VS Code observes as no active terminal) no longer leaves the flag stale. Previously a stale flag made the next click on that loop row fire a no-op `closePanel` instead of `show()`ing, requiring two clicks to reopen. This is Option A from the story's implementation choices (a self-healing visibility signal) over Option B (gating the close branch on `activeTerminal` at click time), since Option B would still read the stale terminal as "active" the instant the panel closes and reproduce the same no-op. Change confined to `src/terminals.ts`; the CMD+J-is-native-VS-Code explanation stays documentation-only, no keybinding added. Manual F5 confirmation still pending (headless session).
- All three loop-row buttons schedule on RIGHT-click (t-77d1): ▶/♻/■ keep their original left-click meanings — start, restart, stop this loop NOW, via the unchanged `spawnLoop`/`recycleLoop`/`stopLoop` messages — and each button's `contextmenu` opens a small popover (`media/sidebar.js` + `media/sidebar.css`) scheduling that same action, carrying preset minute values, a `Custom…` free-text field, and `repeat`/`force` checkboxes. The first cut removed the immediate `recycleLoop` message and put the popover on ♻'s left-click; the human rejected that (t-77d1 feedback, 2026-08-28): the instant action is the common one and must stay a single click, so scheduling — the rarer one — takes the secondary gesture, and the same gesture then generalised to all three buttons. Keyboard users open it the way they open any context menu (Menu key / Shift+F10 with the button focused). Scheduling is deliberately NOT gated on the loop's current state (human, 2026-08-28): a schedule is armed against the state the loop will be in LATER — "stop it in 4h" on a loop you are about to start — so tying the right-click to the left-click's availability blocked the useful cases. Because a real `disabled` button fires no mouse events at all, the inapplicable state is `aria-disabled="true"` + an `.off` class carrying the old `[disabled]` styling, with the click handler simply not bound; left-click behaviour is unchanged. The state check moves to fire time instead: `appliesTo(action, running)` SWALLOWS an action that no longer matches (the human's example — a restart armed for a loop that is already stopped does nothing rather than silently starting it), and the schedule still counts as fired, so a one-shot disarms and a repeat keeps its cadence rather than stacking. ONE schedule per model regardless of which button armed it — "start in 5m" and "stop in 10m" on the same loop are contradictory, so arming replaces whatever was armed, and the popover only prefills from the armed schedule when its `action` matches the button being right-clicked. `force` exists only for restart and stop, the two that can kill a working terminal: `supportsForce` gates the checkbox, `armSchedule` coerces a start's force to false, and `mayFire` short-circuits a start so it never defers (there is no worker to cut off). A webview popover over a chain of native prompts (human decision): the three controls are one decision and must be visible together, which `showInputBox`/`showQuickPick` cannot do; those two APIs stay unused in `src/`, and the "pick list" is popover markup. MINUTES are the only unit — no hours/days selector — and `parseMinutes` rejects anything that is not a plain positive integer (no `90m`, no `1.5`, no decimals) so a value can never be silently reinterpreted; it also rejects anything that would overflow `setTimeout`'s signed-32-bit delay, which otherwise fires immediately instead of far in the future. Schedule state is SESSION-ONLY in the controller (`restartSchedules`/`restartTimers` maps): nothing reaches `globalState`, `workspaceState` or `.loopboard/`, because the terminals themselves die with the window and a schedule outliving its terminal is meaningless — `workspaceState` is not even wired into the controller. Consequently this feature writes no `.loopboard/` file at all and its debug-trace obligations are just the popup/choice pair plus `restart-arm`/`restart-fire`/`restart-defer`/`restart-cancel` at `info`. All the decidable logic lives in a pure `src/schedule.ts` (added to `tsconfig.test.json`, unit-tested in `test/schedule.test.js`): `mayFire`, `deferSchedule`, `afterFire`, `parseMinutes`, `describeSchedule`. Deferral (force off) reuses the idle edge `maybeAutoRecycle` already detects rather than adding polling — "is this loop busy?" is knowable ONLY from `.loopboard/TODO.md`, since terminal output can never be read — and waits INDEFINITELY with a visible pending indicator, never expiring, because the entire point of leaving `force` off is "restart it, but not while it is working"; `afterFire` re-arms a repeating schedule from the moment it actually fired, not its original slot, so a long deferral cannot produce a burst of catch-up restarts, and `deferSchedule` is idempotent so at most one restart is ever pending per model. Force consent is a native modal taken ONCE when the schedule is armed, not at fire time (human decision): a restart scheduled hours out is unattended by definition, so a fire-time modal would either block the restart the user asked for or pop over unrelated work long after the decision. The modal names the real consequence — the extension never edits a task's `phase:`, so a forced mid-task kill leaves the task `inprogress` with no worker and LOOP.md Rule 2's global single-task limit then blocks every loop until a human fixes it by hand.
- Loop steering lives in the EXTENSION, and a nudge is a hint rather than a work order (t-068e). The extension already sees every board change (the `.loopboard/**/*.md` watcher in `src/store.ts`) and owns the loop terminals, so it — not any loop — decides who has something to do: `src/nudge.ts` (pure, unit-tested) routes each CHANGED task to exactly one loop per the Rules 14/15 ownership split (New/DRAFT by `groomer:`, Backlog onward by `model:`, absent = the matching default, `groomer: none` = on hold and never nudged), and `controller.maybeNudge` pastes one line naming those specific tasks into that model's terminal. Change detection reuses `rev:` (Rule 17) with `raw` as the fallback for pre-`rev:` trackers — no new machinery, and nothing here ever writes `rev:` or edits `model:`/`groomer:`, so steering can never reassign work. Delivery is IMMEDIATE and deliberately cannot interrupt: `terminals.nudge` uses the same paste-then-lone-Enter machinery as `/clear` (`sendText(text, false)` + Enter after `SUBMIT_DELAY_MS`), which only seeds the REPL input. It is one-way by necessity — terminal output can never be read — so there is no ack, no retry and no queue on disk: a model with no terminal has its nudge HELD in a session-only map (like the restart schedules; the terminals die with the window) and delivered on the next refresh that finds one, de-duplicated per task id so ten edits during a down loop produce one line. Two suppressions keep a nudge from ever meaning "do nothing": a task that gives no loop work (In Progress, Review with no `feedback:`, a New task whose answers are all blank) routes nowhere, and a Backlog "claimable" nudge is dropped entirely while any task is `inprogress`, since Rule 2 forbids the claim anyway. The first board load of a session nudges nobody — everything would look new. Nudging SUPPLEMENTS the every-pass board re-read, which stays the source of truth, so a missed or disabled nudge (`loopBoard.nudgeLoops`, default true) changes no correctness property; the template gained one terse Notes bullet saying exactly that, so a nudged loop treats the line as a hint and still lets the Rules decide.
- Settings restructured around ONE 3-state `loopBoard.afterTask` and native rows, not a custom settings webview (t-1f1e). The per-slot model data already had the shape the human's "grid" asked for (tick `enabled`, then optionally type a custom `--model`); what was missing was presentation, and VSCode's native settings page cannot render a grid or conditional fields at all — so the slots stay flat rows, tightened into three visual blocks by ordering (10-12/20-22/30-32) and a bold `**<Slot> slot.**` lead on each `enabled` description. A custom webview (real grid + a `getConfiguration().update()` write path) is deferred until the tidied native page proves insufficient. `autoRecycle` + `clearSessionAfterTask` collapse into `loopBoard.afterTask` = `none` | `clear` | `recycle`: the pair was never two independent switches — `maybeClearSession` was skipped outright whenever `autoRecycle` was on — so the enum is lossless (both false → `none`, clear → `clear`, auto (whatever clear says) → `recycle`) and the exclusivity that used to be an explicit guard is now structural. Migration is read-both with `markdownDeprecationMessage` on the old keys and NO write to user config, mirroring `readModelsConfig`'s legacy-shape fallback; the load-bearing detail is that `get()` cannot express "unset" for a key with a non-null default, so `readAfterTask` uses `inspect()` and consults only values the user actually set, or the new key's own default would silently beat a legacy value. Resolution lives in pure `src/model.ts` (`resolveAfterTask`, unit-tested) rather than the controller, which keeps the only vscode-facing part the three-line `inspect()` read. The audit also fixed a real defect — `customRules` and `debug` both carried `order: 5`, leaving their relative position to chance — and folded the one-key "LoopBoard: Permissions" group into Loop Behavior: `permissionMode` is spawn configuration like `loopInterval` beside it, and a group of one is pure overview cost. Both spawn-frozen keys now say so in their descriptions, since neither reaches a running loop without a ♻.
- Re-groom resumes the original grooming subagent instead of always re-spawning (t-9e18): Rule 14's re-groom clause in `media/template-loop.md` now says to resume the groomer that first groomed the task (SendMessage by agent id — verified by live experiment that a COMPLETED subagent stays resumable with full context, and that SendMessage was available with no env flag set) and to fall back SILENTLY to a fresh spawn on any resume failure (recycled/cleared session, window reload, no SendMessage, unknown id). Instruction-only change: `src/terminals.ts` untouched (no env plumbing), no new index/Meta key — the agent id lives only in the loop session's memory, so a recycle simply degrades to today's behaviour. Grooming-only scope; t-e3c3's story carries a note to adopt the same pattern for its delegated implementer/review subagents.
- `loopBoard.customRules` is workspace-ONLY (t-22ad): the setting writes a git-tracked file into the workspace, so a User-level (global) value is never applied — previously an unscoped `c.get` returned the merged global value in EVERY open window and one Settings-UI edit rewrote N workspaces' LOOP.md at once (the live listener plus activation/Sync all funnel into `applyCustomRules`). Fix is two-part because a `scope` declaration alone cannot forbid a User-level value: `package.json` now declares `"scope": "resource"` (documentation + proper workspace override in the UI), and `controller.applyCustomRules` reads via `inspect()` through pure `selectWorkspaceRules` (`src/customrules.ts`, unit-tested) taking `workspaceFolderValue ?? workspaceValue ?? []` and NEVER `globalValue`; a present global value is only debug-logged at `info` as ignored. No migration by design (human decision): a rule already at User scope simply stops applying, cleanup of user settings.json stays manual. Other settings' scopes stay with t-1f1e.
- Finishing a task has a STRICT order, and the Review move is its LAST action (t-16d2): Rule 11 already made the In Progress move lead the work, but nothing made the Review move trail the push — a worker could set `phase: review` and only then commit, so any interruption left a Review task whose branch was missing or stale. `media/template-loop.md` now states the order in one place per surface: Rule 7 pulls `## Delivered` into its "before setting `phase: review`" clause alongside `link:`; Rule 12 replaces the "before the session ends" deadline with "BEFORE `phase: review` is set … after a succeeded push", mirroring Rule 11's leads/trails wording; Rule 13 routes the feedback round-trip through the same order; and the Automation fence's "When finished, …" sentence became an explicitly numbered FIRST/THEN/ONLY-after sequence (also fixing the "if you the user" typo). Instruction-only: `src/sync.ts` and `src/loop.ts` are untouched, PRs stay optional (Rule 7), and this repo's workspace-only "PRs must be created before moving to in review" custom rule deliberately does NOT enter the template. `test/loop.test.js` gained an assertion that the Automation fence still names the Review move as the LAST action and orders commit-and-push before it, so a later compression pass cannot silently drop the guarantee; the file lands at 223 lines against `test/template-budget.test.js`'s 228 cap. Note for future editors: the fence is NOT apostrophe-free (t-16d2's story claimed it was) — that constraint belongs to `buildLoopCommand`'s short bootstrap line, which is what `test/loop.test.js` actually asserts.
- The grooming concurrency cap is per-slot and rides the SPAWN-TIME bootstrap prompt (t-23ce): `loopBoard.models.<slot>.groomConcurrency` (number, minimum 1, default 3) bounds how many grooming subagents one pass of one loop may run. Per-slot rather than global because grooming routes by `groomer:` and the eligible set is wildly skewed between slots; per-pass-of-one-loop rather than board-wide because the only shared state is `.loopboard/` markdown and the fixed index grammar (Rule 4) forbids the claim marker a board-wide ceiling would need — two loops grooming concurrently can together exceed any single slot's number, and that is accepted. Deliberately NO `0 = unlimited` sentinel: unbounded fan-out is the defect the cap removes, so it must not stay reachable through configuration; anything non-integer or out of range falls back to 3 (`sanitizeGroomConcurrency`) rather than reaching the single-quoted shell line raw. The NUMBER can only ride the prompt — `syncMarkedSections` copies template blocks byte-for-byte with no interpolation anywhere in the sync/scaffold path, so a number written into `media/template-loop.md` would be a constant identical in every workspace — while the BEHAVIOUR (groom up to the cap in index order top down, leave the surplus for the next pass, report skipped tasks by title) lives in Rule 14 and the Automation block, phrased against "the grooming cap named in your bootstrap prompt" so it needs no number. Consequence, documented rather than engineered around: a running loop keeps the cap it was spawned with, so a change applies only on that slot's next ▶/♻ — no `onDidChangeConfiguration` listener is added for it. The cap is an instruction, not a mechanism: the extension can never observe or block a subagent spawn, so compliance is best-effort by the worker.
- A finished task does NOT end the pass — loops re-run until idle (t-ff77): with `loopBoard.afterTask` at its `none` default nothing re-triggered a pass after a delivery except the `/loop` tick, so every finished task cost up to a full interval (now 5m, t-2625) of dead time while the next Backlog task, a mid-task answer or a `note:` sat waiting. The nudge (`loopBoard.nudgeLoops`) could not close this: the template makes it "a HINT ... never a work order", it only seeds the REPL input, and it is held while the terminal is down. Since the extension cannot read terminal output, the fix can only be instructional: the Automation fenced block in `media/template-loop.md` now ends the delivery/Feedback sentences with a clause stating that whenever the task the worker holds leaves `phase: inprogress` — delivered to Review OR parked in Feedback (both settled human decisions) — it STARTS OVER from the top of the block in the same pass, repeating full passes until one ends with "nothing claimed and nothing reconciled", and NEVER idles until the next tick while eligible work remains. That terminator is what keeps it safe: a pass whose only outcome is "something is in progress — skipping prepared task" or "no changes" ends the cycle, and grooming New tasks never counts as a claim, so an all-grooming pass cannot spin. Rule 2 already permitted the re-claim (the worker's own task left the single In-Progress slot when it moved to Review), so this adds no concurrency — it just runs the existing gate sooner. No new numbered rule (Rule 18 would cost ~3 of the ~5 remaining budget lines) and no extension-side mechanism: `buildLoopCommand`, `maybeNudge`, `maybeAutoRecycle`, `maybeClearSession` are untouched. The fence is one physical line, so the file stays at 223 lines under the 228 cap; the stale "default 1m" note was corrected to `5m` in the same edit. `test/loop.test.js` pins the clause, its terminator and its position after the delivery sentence via a shared `automationFence` helper.
- Context usage is READ FROM THE TRANSCRIPT and a threshold restart never interrupts a worker (t-2b89): Claude Code persists no context number the extension can ask for. `~/.claude/sessions/<pid>.json` exists only while a process lives and carries identity (`sessionId`, `cwd`, `name`, `status`) but NO token counts and no model; the numbers live in `~/.claude/projects/<encoded cwd>/<sessionId>.jsonl`, where the last main-chain `"type":"assistant"` line's `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` is the current window size (output tokens are not in the window; `"isSidechain":true` lines are subagents and are skipped). The status-line hook's `context_window.used_percentage` reaches no file, so it is unusable here. Matching a slot to a session needed a new spawn flag: every loop terminal shares the workspace `cwd` and the session JSON records no ppid, so `buildClaudeBase` now appends `--name loopboard-<slot>` (chosen over pinning `--session-id`, because `/clear` starts a NEW session id in the SAME process — the name survives, the id does not). Parsing is pure and unit-tested (`src/context.ts` → `test/context.test.js`); the vscode half is a thin reader (`src/contextreader.ts`) that reads through `vscode.workspace.fs` on absolute paths OUTSIDE the workspace — deliberately not `store.ts`, which owns `.loopboard/` and nothing else — with a minimal ambient `declare const process` for `HOME`/`USERPROFILE`/`CLAUDE_CONFIG_DIR` since `@types/node` stays forbidden. Polling (30s `setInterval` in the controller) beats a watcher: transcripts are append-only multi-MB files, so each poll `stat`s first and only re-reads when the size changed, then decodes just the last 256 KB. Window size cannot be read at all — it is derived from the slot's `--model` string (`[1m]` → 1,000,000, else 200,000), so the story's "500k" is 50% of a 1M slot. The threshold (`loopBoard.contextLimit.percent`, 0 = off, and `loopBoard.contextLimit.action` = `clear` | `recycle`, its own setting rather than a mode of `loopBoard.afterTask`, whose `none` default has no meaning here) is ALWAYS deferred, never forced (human decision): killing a worker mid-task leaves its task `phase: inprogress` with nobody on it, which Rule 2 turns into a board-wide block — so a trip while the slot owns the In-Progress task becomes pending and fires on the same idle edge `maybeAutoRecycle`/`flushPendingRestarts` already watch, the tracker being the only knowable "busy" signal. Force stays a right-click-schedule-only choice (t-77d1). A context trip and a timed schedule are INDEPENDENT mechanisms that coexist on one loop (human decision): the trip is its own controller state (`contextUsage`/`contextTripped`/`contextPending`), NOT an entry in `restartSchedules`, so the one-schedule-per-model invariant stays a rule about TIMED schedules only; whichever fires first restarts, and the other re-evaluates against the new session. Hysteresis is by session id — the session that tripped is recorded before acting, so a loop parked above the threshold restarts once, not every poll — and any restart of that loop (timed, manual ♻, stop, `afterTask`) clears the trip, since the measurement belonged to a session that no longer exists. Every layout here is documented by OBSERVATION on macOS (CLI 2.1.260) and is internal to Claude Code, so every read is guarded and any miss degrades to "no indicator, no restart": the sidebar bar renders only for a running loop with a real measurement, never a "0%" lie.
- Correction to the above (t-2b89 review feedback): the context WINDOW is not derivable from the `[1m]` suffix. A live loop spawned as plain `--model sonnet` reported `61k/1000k` in its own status line while the sidebar showed `48k / 200k · 24%` — the 5-series models carry the 1M window natively, with no suffix. Verified against the model registry inside the 2.1.261 CLI binary: `opus-5`, `sonnet-5`, `fable-5`, `opus-4-6/4-7/4-8` and `sonnet-4-6` are `1e6`; `opus-4-1/4-5` and `sonnet-4-0/4-5` are `200000`. Nothing writes the window to disk (the CLI computes it in-process), so `windowSizeFor` now takes the model id from the TRANSCRIPT line it measured — what actually ran — preferring it over the configured `--model` string (an alias, an org name, or stale relative to a running terminal), resolves the bare slot aliases `opus`/`sonnet`/`fable` to their 5-series ids, and keeps an explicit `[1m]` suffix as an override. An unknown id still falls back to 200k, which is the eager direction for the threshold, so the list is explicit and must be re-checked when a new model ships. The same feedback also showed the bar trailing the conversation by up to a poll, so `refresh()` now triggers a measurement too (stat-gated, fire-and-forget, guarded against overlap) — a loop's turn ends by writing `.loopboard/` markdown, which is what fires a refresh.
- A restart now REMEMBERS the session it ended instead of forgetting it (t-c7a2): `contextEnded: Map<Model, string>` beside the other session-only context state, and any reading still carrying that id is discarded whole before the threshold is looked at (`isStaleSession` in `src/context.ts`, unit-tested). The bug was three correct things lining up: `TerminalManager.recycle` respawns 400 ms after dispose and BOTH terminal events poll, so a poll runs seconds before the new `claude` has written `~/.claude/sessions/<pid>.json`; until then the only file matching our `--name` + cwd is the ended session's, so `newestPointer` resolves the dead id and `readUsage` serves its pre-restart number straight from the per-session-id cache; and every restart path wipes `contextTripped`, the one marker `shouldTrip` uses to suppress a repeat — so the stale value counted as a NEW trip. Observed as `context-trip opus 41%` logged 280 ms after `loop-spawn` (the killed session's number, on a process that had not booted — `BOOT_DELAY_MS` is 3500), and on a board with nothing In Progress as three `loop-recycle` inside one second. The guard is keyed on the session id, never on time: an id never comes back (`/clear` mints a new one in the same process, a respawn is a new process) whereas every timing here is a guess. It is populated in all three wipe paths — `clearContextTrip`, `fireContextRestart` (the path the storm took, and the only one for `action: 'clear'`, which raises no terminal event) and `pollContextOnce`'s stopped-loop branch (which runs during the recycle's 400 ms gap) — via one `rememberEndedSession(model)` helper that moves the id across and drops the measurement. `clearContextTrip`'s early return had to go: it skipped a loop that never tripped, whose ended session's bar would otherwise linger (threshold 50, loop at 41%, ♻ → the row keeps showing 41%); remember-then-drop is now unconditional and only the `context-clear` log line stays conditional. A stale reading is not stored either, so the row shows NO bar rather than a stale one — the human's decision, since a stale number was the whole complaint. `contextEnded` is released only by a reading with a different id, deliberately not by ■ or ▶ (a ▶ after ■ is a new process with a new id, so the guard is inert there and still covers the same race). Degradation is unchanged: if the new process never writes a session file the slot simply shows no bar and never trips, which is the "no indicator, no restart" contract. Controller wiring imports `vscode` and so is manual-only: VERIFICATION.md item 32.
- Delegated-work mode is two global booleans riding the bootstrap prompt as a phrase, with the behaviour in LOOP.md (t-e3c3): `loopBoard.delegateWork` (default off) and `loopBoard.delegateWork.review` (default on, meaningful only while the first is on) are read in the `getConfig` closure `src/extension.ts` hands `TerminalManager`, threaded as the sixth/seventh `buildLoopCommand` parameters, and appended as ` Delegate work to subagents.` / ` Delegate work to subagents without review.` — the off-flag prompt is byte-identical to before apart from `grooming effort ceiling` → `subagent effort ceiling`, since the one per-slot `.effort` now caps grooming, implementer and review subagents alike (human decision: no second effort knob, no per-slot delegation flag, no configurable implementer model). The phrase only names the mode; the `DELEGATED-WORK MODE` clause appended to the Automation fence (0 lines, so inside the template budget) spells out the three modes: off = today; on = every code-editing path goes to ONE implementer subagent on the slot model that branches/commits/opens the PR while the main loop keeps every `.loopboard/` write (Rule 11 needs the claim before any work, so the claim cannot live in the subagent); on-with-review adds a sequential review subagent whose pass lets the loop `gh pr merge --squash --delete-branch` before `## Delivered`/`link:`/`phase: review` (Review = merged, awaiting the human tick — no self-accept), and whose fail is re-delegated once then parked in Feedback with the findings as questions, PR left open. With review off the loop does NOT merge (no automated gate → the PR goes to Review unmerged, like today) — stated as an assumption in the story, not asked. Both flags are spawn-frozen like the interval (no `onDidChangeConfiguration`, still none in `src/`); the grooming concurrency cap stays grooming-only because implementer and reviewer run one at a time. - Every `loopBoard.*` property is declared `"scope": "application"` (t-sgrp) — no LoopBoard setting is configurable per repository, full stop. The key that makes it a security matter is `loopBoard.permissionMode`: it is passed to the CLI as `--permission-mode` when a loop spawns and `bypassPermissions` is a valid value, so without a scope a cloned repo could decide how much authority the agent runs with. `application` rather than `machine` because both refuse `.vscode/settings.json` but `machine` still permits REMOTE settings, and a dev container's settings come from `.devcontainer/devcontainer.json` — which ships inside the repo, leaving the same door open through a second channel. `application` is user-settings-only and is the flavour Settings Sync propagates. The three `models.*.model` strings are not in the same risk class (`isValidModelString` already allowlists them before the shell line), but they go `application` too, for the single simple rule. Accepted cost: VSCode silently ignores rather than migrates an existing workspace value, so README carries a migration note; and a repo can no longer ship team defaults. Enforced by `test/manifest-settings.test.js` with no exception list, so a future key added without a scope fails the suite rather than quietly becoming workspace-settable.

Liveness comes from files Claude Code leaves behind (undocumented, macOS/CLI 2.1.276, re-verified on the implementing machine): `projects/<slug>/<sessionId>/subagents/agent-<id>.meta.json` is the spawn record, `agent-<id>.jsonl` its own transcript, and the finish/resume markers live in the PARENT transcript — a `<task-notification>` with a terminal `<status>` for async agents (written twice per finish, deduped by id), an ordinary `tool_result` on the meta's `toolUseId` for sync ones, and a `SendMessage` with `input.to` re-opening a finished one (latest marker wins). The one trap, which cost a full debugging round in grooming: EVERY Agent call gets a `tool_result` on its `toolUseId` at spawn time, and for an async agent that result starts with `Async agent launched successfully` and is a receipt, not a finish — `requestShape` is NOT the discriminator, since metas without it were async too. The staleness backstop is what keeps the hold safe: an agent counts live only if its own transcript was written within `AGENT_STALE_MS` (30 min), because `findSessionId` can resolve a pointer file a SIGKILLed process left behind and its metas would otherwise have no finish marker forever — such leftovers now age out, logged at `verbose` so a restart that suddenly fires is explicable. - Follow-up to the above (t-sbag, PR #157 review): a HELD afterTask action is now gated by the pure `resolveHeldAfterTask(mode, running)` in `src/model.ts` and cancelled by every path that restarts the loop some other way. Three bugs, one root cause — the hold outlives the state it was recorded in, and `TerminalManager.recycle` disposes only IF a terminal exists but ALWAYS respawns 400 ms later, so firing it at a stopped slot is a plain START. (1) A hold surviving a manual ■: the human stops the loop, the not-running branch of `pollContextOnce` sets `busyChanged`, the flush trio runs, `busyModels` no longer contains the model and a fresh `claude` spawns seconds after the human killed it — exactly what CLAUDE.md forbids for the sibling mechanism ("SWALLOWS an action that no longer matches … never a silent start"). (2) A second recycle on top of a normal one: `maybeAutoRecycle` fires at :319 and `flushAfterTask` four lines later fires again for the same model, two dispose+respawn pairs racing in one 400 ms window. (3) The same double-fire through a manual ♻, which made that button non-idempotent whenever a hold was pending. The fix is two rules, both mirroring machinery that already existed: an action that no longer applies is SWALLOWED rather than turned into something else (`appliesTo` for schedules, `resolveHeldAfterTask` here — `not-running` outranks `off` so the log names the real reason, and gating `clear` on running also stops `clearSession`'s silent early return being logged as a success); and any restart by any path satisfies the hold, hooked into `clearContextTrip` — which every restart path already funnels through for exactly the same reason — plus explicit `cancelAfterTask` calls on the two paths that do not (`fireContextRestart`, the poll's not-running branch). Same review also: `scanMarkers` takes the session's KNOWN agent ids/toolUseIds and drops markers naming anything else, because a synchronous agent finishes via a plain `tool_result` and without the filter every tool call in a 10 MB transcript was recorded as an agent finish and retained for the life of the window; its dedupe is now by id with the seen set carried across chunks (a notification's two halves need not be adjacent, and the byte-delta cut can land between them) and cleared by a `SendMessage` resume, so a resumed agent's next finish is still reported; and `readAgentStart` caches the NEGATIVE answer, since an agent whose opening prompt exceeds `AGENT_HEAD_BYTES` would otherwise re-read its whole growing transcript every 30 s for a duration string.
- Two human-observed corrections to t-sbag's Agents section (PR #157). (1) A RESUMED agent's duration counted the idle gap since its original spawn — observed as a row reading `14m` while that agent's own status line read `59s`. Cause: `startedAt` comes from the first line of `agent-<id>.jsonl`, and a `SendMessage` resume keeps the agent id and APPENDS to the same transcript, so that line still holds the spawn instant; the row therefore reported spawn-to-now, including however long the agent sat finished in between. Resume is a first-class path here (delegated-work mode resumes implementers, reviewers and groomers constantly), so this was wrong on exactly the agents the section exists to explain. `relived` markers now carry the transcript line's own ISO `timestamp` (verified present on the `SendMessage` assistant line), `foldAgents` substitutes the latest DATED resume for the spawn, and `describeAgent` stays a pure formatter. An undated resume keeps the last dated one rather than falling back to the spawn — a stretch measured from an earlier resume is far closer to the truth than one that includes every gap since creation. (2) `AGENT_STALE_MS` raised 30 → 60 minutes. The cut reads MTIME, not age, so an agent that merely lives a long time was never at risk; the real hole was an agent blocked on ONE long operation (Docker image build, slow test suite, network wait) writing nothing for the duration, being dropped from `agentBusy`, and a held restart then killing it mid-work — the precise outcome the story exists to prevent, caused by its own backstop. Deleting the cut was not an option (it is the documented answer to the `findSessionId` stale-pointer risk: a SIGKILLed session's leftover metas would hold every restart forever). A marker-aware cut — only drop on silence when the session pointer is gone — was considered and REJECTED on evidence: every cheaper liveness signal available is either the stale-pointer risk itself (the pointer exists), documented as unreliable (`updatedAt`/`statusUpdatedAt`, which the story observed frozen two hours into a live session), or goes quiet for the very same reason the agent does (the parent transcript's mtime — a parent waiting on silent agents writes nothing either). Trading a bounded 60-minute exposure for an unbounded "held forever" is the worse bug, so the hour is paired with an `agents-stale` line that states plainly the agent was dropped for SILENCE rather than for finishing and that a held restart may now fire.
