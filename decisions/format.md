# Decisions — Index & task-file format

One line each: what, why. Newest at the bottom. Index: [../DECISIONS.md](../DECISIONS.md).

- Board carries structural `phaseHeadings` + `sectionExtras` (attached as non-enumerable-ish props via helpers `getPhaseHeadings`/`getSectionExtras`) so exact section headings and HTML-comment templates round-trip verbatim without bloating the documented `Board` interface.
- Parser strips leading `❓`/`⚠️` from question/feedback text and the writer re-adds them — canonicalizes emoji placement so a file missing them normalizes cleanly.
- Model split into `IndexEntry` (index file) + `TaskDetail` (task file) + composed `Task = IndexEntry & TaskDetail & { hasDetailFile }` (view/webview shape stays stable); `Board` drops `automation` (loop instructions moved to LOOP.md) and its `done` is now `IndexEntry[]`. Parser returns an `IndexDoc { preamble, entries }`.
- Task-file format (`taskfile.ts`, pure) has no frontmatter — the index owns title/phase/model/groomer/questions; the writer rewrites the H1 from the index title on every save and emits fixed heading order (Meta/Description/Notes/Worklog/Feedback/Delivered), omitting empty sections; unknown headings/keys round-trip verbatim at the end (keeps the fixpoint idempotent). `## Notes` is a bullet list → `notes: string[]`.
- New Story drafts always carry explicit `groomer:` + `model:` in the index: `Controller.onMessage('createDraft')` resolves an empty composer selection to the configured `defaultModel` (opus) so an ungroomed draft is never left to the implicit "no field = default" routing — a loop can tell unambiguously who grooms and who works it; a non-default pick lands verbatim. Grammar keys stay `groomer`/`model` (unchanged); only the composer UI relabels the worker selector "Model" → "Work with" (groomer stays "Groom with").
- Per-task `rev:` change marker in the index (t-9d5c, builds the t-2a06 concept): an optional monotonic integer on each `.loopboard/TODO.md` entry (grammar v4, fixed order after `groomer:`), so a loop worker reading ONLY the slim index each pass can tell WHICH task(s) changed — including a human edit buried in `tasks/<id>.md` (the original miss on t-5e1a that motivated this). The WRITER (not readers) manages it: `store.ts` computes each touched task's canonical fingerprint BEFORE and AFTER a write — the index block via `serializeEntry` with `rev` excluded (so re-emitting a bumped rev is not itself a "change" → no self-perpetuating bump) plus the `tasks/<id>.md` text — and bumps `rev` iff they differ, on `applyFieldPatch` (index + detail), `promote`; `acceptToDone`/`deleteTask` remove the entry entirely (the "id gone" signal) and `createDraft` adds a new id (the "id new" signal), so neither bumps. Readers NEVER write just to detect a change, so multiple loops (opus/sonnet/haiku) polling constantly never perturb the file or trip each other. Parser tolerates a missing `rev:` (defaults absent/0) and a non-integer value lands in `unknownLines`. Deliberate consequence, accepted by the user as the one slim-index expansion: a DETAIL-file patch now also writes `TODO.md` to persist the bump (the extension's "one file per save" pattern yields here because the whole point is surfacing detail changes in the index). The loop-side "compare each id's rev to last pass" logic is worker behavior documented in LOOP.md Rule 17 / the shipped `media/template-loop.md`, not extension code. `template-todo.md` intro left unchanged (rev is extension-managed, not human-authored; full grammar authority is LOOP.md).
- Review feedback moved from the task file's `## Feedback` section to a repeatable index `feedback:` sub-bullet (t-fbi1), mirroring `note:`: `feedback` is now an `IndexField` (patches `TODO.md`, get/set join/split on `\n` like notes) instead of a `DetailField`, so a loop reading only the slim index (read economy) can see pending Review feedback without opening every task file — and it now participates in `rev:` for free (no new rev logic). `taskfile.ts` stops parsing/writing `## Feedback` entirely; a pre-existing task file with that section keeps it as inert, flagged `unknownLines` content (no migration — human decision, since no live data was at risk and a migration path added complexity for a one-time historical section). The board's Review feedback textarea is unchanged UX-wise; only the storage routing moved.
- Task-file `owner:` field removed entirely (t-33cb): the `@claude`/`unassigned` binary was a fossil of the pre-multi-model board — the GLOBAL SINGLE-TASK LIMIT (LOOP.md Rule 2: at most one `phase: inprogress` task board-wide) was already the sole one-worker guarantee, so claiming is now just `phase: inprogress` (index) + `started:` (task file), with no separate ownership field. Removed from `META_KEYS`/parse/serialize (`src/taskfile.ts`), `TaskDetail`/`WebTask` (`src/model.ts`, `src/view.ts`), the `createDraft` skeleton (`src/store.ts`), the delete-confirmation heuristic (now bare `task?.phase === 'inprogress'`, `src/controller.ts`), and the owner/unassigned board chips + working-indicator text ("Worker is on it…", no attribution) in `media/board.js`/`media/board.css`. A stale `- owner:` line in an existing task file is now a recognized-but-dropped key (`DROPPED_META_KEYS`) — silently discarded on parse rather than falling into `unknownLines`, so it can't relocate to the bottom of the file or spawn a flagged "unparsed line" chip. `.loopboard/LOOP.md` Rules 2/11, the workflow legend, the `## Meta` grammar block, and the `## Automation` fenced block were rewritten to drop every `owner:` reference, mirrored by hand into `media/template-loop.md` (verified identical via diff). Pre-existing `.loopboard/tasks/*.md` `- owner:` lines are left as-is (strip-sweep deferred, not part of this PR) — the dropped-key parse behavior already neutralizes the flagged-chip/relocation churn the human was avoiding.
- "On hold" is a sentinel VALUE on the existing `groomer:` field, not a new key or phase (t-65a2). `groomer: none` means the New/DRAFT task belongs to NO groomer and no loop may groom, re-groom or answer-fold it; absent still means "default groomer", so the change is backward compatible and new drafts keep today's default routing — hold is always an explicit per-task choice in the "Groom with" select. A separate `hold:` flag was rejected because it can contradict `groomer:` (held but routed), which a value of the routing field cannot; a new pseudo-phase was rejected because it would move the entry out of New and lose its human promote gate. The parser change is the load-bearing one: `src/parser.ts` gated `groomer:` through `KNOWN_MODELS` and dropped anything else into `unknownLines`, where an unrecognized value reads as ABSENT = default groomer — the exact opposite of hold — so `none` had to become an explicitly recognized value (`GROOMER_HOLD`/`GroomerValue` in `src/model.ts`). `src/merge.ts` gained `normalizeGroomer` (the sentinel plus everything `normalizeModel` accepts) for the groomer patch and `store.createDraft`; `normalizeModel` itself is untouched, so `none` is still not a valid WORKER model. The writer needed no change — it already serializes `entry.groomer` verbatim, so the fixpoint holds for free. On the board, only the two "Groom with" selects (composer + draft card) gain the `On hold` option, mapped to/from the wire value `none` by `normGroomerValue`/`groomerSelectValue`; the worker-model selects do not, because hold is a grooming-axis choice. A `.qa-pending`-styled "on hold — not groomed" badge (reusing t-6936's badge styling) renders on New/DRAFT cards so the state is visible without opening the select, and the draft card's "the loop will structure this into a story" hint is swapped for its held wording. Rule 14 and the Automation fenced block in `media/template-loop.md` gained the hold clause (mirrored by hand into this repo's gitignored `.loopboard/LOOP.md` so running loops obey immediately — `store.autoHeal` is create-only and marked sections otherwise reach a workspace only via the manual Sync command); rule numbering 1–17 is unchanged.
- `rev:` REMOVED from the index grammar (t-f1b0, reverses t-9d5c): the per-task change marker is gone from `IndexEntry`, the parser's canonical keys, the writer, and every `store.ts` bump site (`indexFingerprint`/`bumpRev` deleted) — the human's call, on the premise that the direct push (the t-068e nudge the extension pastes into a running loop) now carries change detection, so a polling marker whose comparison BASELINE was the worker's context window (lost on every `/clear`, recycle and fresh spawn) is redundant, costs a second `TODO.md` write on every detail patch, churns most entries on every edit, and adds a key no human ever writes. Accepted losses, taken with the evidence in view: a task the nudge deliberately never routes (In Progress, `groomer: none`, a Backlog nudge suppressed while anything is In Progress), `loopBoard.nudgeLoops: false`, and edits made with no extension running now have NO change signal at all beyond re-reading every task file. Hard precondition shipped in the same change, because the nudge itself was built on `rev:`: `nudge.changed()` is now an index+detail TEXT fingerprint (`raw` + the new `detailRaw`, which `store.compose` keeps because the `IndexEntry`/`TaskDetail` spread collapses both `raw` keys), so a `tasks/<id>.md`-only edit still nudges — without it the removal would have amputated exactly the capability it leans on. Migration is recognize-and-drop, the precedent `owner:` set in `taskfile.ts` (t-33cb): `case 'rev'` stays in `parseEntryBlock` and consumes the line for ANY value, so a stale `- rev: n` never reaches `unknownLines` (which would relocate it to the entry's bottom and draw a flagged chip on every card) and simply vanishes on the next canonical write — no one-shot migration pass, no activation rewrite, fixpoint intact. Restored consequence: a detail-file patch (and an attachment append, and a description-only detach) writes ONE file again, so CLAUDE.md non-negotiable 4's one-file-per-save has no exception left. LOOP.md Rule 17 and the grammar line are gone from `media/template-loop.md` (218 lines, budget 228); rule numbering is now 1–16.
- Task file gains two optional groomer-owned sections around the story (t-2191), canonical order `## Meta` → `## Problem` → `## Description` → `## Goals` → `## Worklog` → `## Delivered`: `## Problem` says WHY the task exists (short, factual), `## Goals` says what "done" means (a bullet list), and the review judges `## Delivered` against `## Goals` goal by goal — a missed goal is a review FAIL, not a finding. Both stay FREE MARKDOWN in storage, exactly like `## Description` (`case 'problem'`/`case 'goals'` in `src/taskfile.ts` mirror the description case; `DetailField` in `src/merge.ts` gains both, so `patchTarget`/`applyDetailPatch`/`store.applyFieldPatch` carry them with no new machinery and a save still writes ONE file): the parser validates NEITHER Problem's length nor Goals' bullet shape, so a Goals section written as prose still round-trips and the "short and factual"/"bullet list" demand lives in LOOP.md's task-file-format block, not in a grammar. Goals are plain `- ` bullets, never `- [ ]` task-list items — `media/markdown.js` has no task-list support (a `- [ ]` line renders as literal text) and `[x]` already means "human gate" on the index. No backfill and no migration pass: both sections are optional, existing task files parse unchanged, and a hand-written `## Problem`/`## Goals` that used to land in `unknownLines` at the BOTTOM of the file is now recognized content that relocates to its canonical slot on the next save (same recognize direction as the dropped `owner:`/`rev:` keys). The worker prohibition ("a groomer writes Problem/Goals, a worker never edits them") is LOOP.md rule text ONLY — Rule 4, Rule 14, the task-file-format block and the Automation fenced block — with no mechanical guard, because the extension cannot attribute a `tasks/<id>.md` write to a worker versus the human and any guard would flag legitimate human edits; on the board both sections are editable exactly like Description (human decision). One renderer serves all three: `media/board.js`'s `renderDescription` became `renderDetailSection(t, section)` driven by the `DETAIL_SECTIONS` table (field name keys the fold state, `data-field`, the patch and the per-field `ui[id]` editor state), so the click-to-edit/Save/click-outside-commit/ESC behaviour cannot drift between sections; only Description keeps ＋ Attach and drop/paste, since `src/controller.ts`'s field-scoped attach allowlist deliberately does not carry problem/goals. `media/template-loop.md` stays at 225 lines against the unchanged 228 budget — the +7 the feature costs is partly paid back by reflowing Rule 3 and the task-index-format paragraph.
- Every index value is ONE line, enforced on the host (t-c4d1, grammar v5 unchanged; amends `decisions/board-ui.md` t-5e6d correction (d) and carries over the 2026-08-22 answer decisions): `canonicalLine` (`src/merge.ts`, pure, exported) folds each run of CR/LF with its surrounding whitespace into one space and trims both ends — exactly what parse→write makes of a single-line value. `applyPatch` stores `title`, `answer`, each answer of `answers` (split positionally on the RAW value, behind the unchanged raw line-count guard, then folded per answer — never the whole value) and feedback through it, and compares CANONICAL current/base/value, so an idempotent re-save with a stale raw base is applied while a real same-field change still conflicts (non-negotiable 4 holds). Problem/Description/Goals are never folded. Merge reports a fold as `canonicalized: { raw, stored }`, and the store logs it at `verbose` (`canonicalize`), so merge stays logger-free. The writer folds title, question, answer, suggestion and feedback in `serializeEntry` and the title in `serializeDoneEntry` as a silent backstop — no current host path can trigger it. Why: before this a multi-line DRAFT title split into unparsed lines, a `- [ ]` line took over the task's id, and an answer could inject a `feedback:` instruction.
- One feedback entry is ONE `feedback:` item (t-c4d1 decision 4, amends t-fbi1's "join/split on `\n`" above and `decisions/board-ui.md` t-ae10): `feedbackLines` returns the entry folded by `canonicalLine`, or nothing when blank, so an add appends at most one item and an edit replaces one item with at most one. A grammar change (continuation lines) and moving bodies into `tasks/<id>.md` were rejected (every loop would delete a multi-line item line by line; t-fbi1 put feedback in the index so a loop reading only the index sees it). No migration: items already split on disk stay separate.
- An unknown `## ` line inside `## Problem`, `## Description` or `## Goals` is story text and stays in place (t-c4d1 decision 6, amends "unknown headings/keys round-trip verbatim at the end" above for those three sections only): while one of the three is open, only one of the six known headings (case-insensitive, surrounding spaces ignored) ends it; Meta, Worklog, Delivered and unknown sections still end at every `^##\s+`. Deliberately NOT fence-aware: in this workspace a fence opener cut off at the end of a Description would pair with a closer after `## Delivered` and swallow the real Worklog/Delivered, and a line starting with an inline triple-backtick span fools a naive toggle. Residual gap (pinned by test H9): a KNOWN heading inside a fence still splits. Every task file in this workspace parses exactly as before (checked against `origin/main`, 189 files).
- An HTML comment in the index opens only at a line whose trimmed text STARTS with `<!--` (t-c4d1): `parseSection` used `includes('<!--')` for both the comment opener and an entry block's end, so an opener inside a single-line title/answer/feedback value moved lines out of the entry or hid every later task in the section extras. Entry lines start with `- [` or an indented `- `, so a value can no longer open a comment; `parseDone` shares `parseSection`, so DONE.md is covered too.
- The New Story composer's RAW text is also copied into a fresh draft's `## Description` when it has more than one line (t-c4d1 decision 5): the index title stays the flattened `DRAFT:` one-liner, and `draftDescription` (`src/taskfile.ts`, pure) strips `loopboard-pending:` placeholders (only the title's are rewritten) and `.loopboard/cache/` links (they stay in the title; `renderAttachmentsArea` would draw a second chip), trims blank edge lines and keeps inner blank lines and indentation. `store.createDraft` writes it into the eager skeleton (t-6ab4). Known edge: a later draft-title edit does not update the copy until grooming rewrites `## Description`.
