# Decisions — Board & sidebar UI

One line each: what, why. Newest at the bottom. Index: [../DECISIONS.md](../DECISIONS.md).

- Ported the design bundle's mockup (`loopboard-vscode-extension/project/board.dc.html`, `sidebar.dc.html`) — a React-like DC prototype — into vanilla `media/*.{html,css,js}`: same regions, type scale (15/13/11), 4px grid, colors via `var(--vscode-*)`, and the two allowed animations (attention pulse, refresh flash) with `prefers-reduced-motion` honored.
- Webview normalizes the model select's `default (opus)` display value to `''` before sending a patch, matching the store's "no model" representation so an unchanged/default model never trips a false same-field conflict.
- Board full-re-renders on each refresh but **defers** applying an incoming board while a field is focused (`pendingBoard`, flushed on `focusout`) so a loop write mid-typing can't discard the user's in-progress input.
- Board content pane is left-aligned against the rail (`.pane-inner` margin 0, not auto-centered) — on wide windows the mockup's centered column left a huge gap after the rail, making the cards look like a detached second menu.
- Board's left rail removed (it duplicated the sidebar): phases are horizontal tabs in a top bar with the New-story button, cards take the full remaining width; loop controls live only in the sidebar and gained a stop (■) button (`stopLoop` → `TerminalManager.stop()` = dispose without respawn).
- Textareas auto-grow after mount via `requestAnimationFrame` in `render()` — `scrollHeight` is 0 on detached nodes, so growing at build time left multi-line descriptions cropped at 2 rows.
- New tasks are approved with an explicit ✓ Approve button instead of a bare checkbox (same `promote` gate); Review keeps the checkbox + confirm since accepting rewrites two files.
- Block-level markdown in card text (t-mkd1): `mdToHtml` (`media/board.js`) is now a line-oriented block pass over the source — ATX headings `#`..`######` → `<h1>`..`<h6>`, unordered (`- `/`* `) and ordered (`1. `) runs → `<ul>`/`<ol>`, everything else = paragraph text with the LEGACY soft-wrap semantics preserved (single `\n` = space, blank line = `<br><br>`, no `<p>` wrapper — plain descriptions render byte-for-byte as before). A new `renderInline(text)` helper (escape → `` `code` `` split → `renderInlineMd`) is reused by headings, list items, and paragraphs so inline bold/italic/code/links work inside every block. The escape-first XSS invariant is intact: the classifier only inspects raw markers, but every user-text fragment is `escapeHtml`'d before it lands in a tag (verified against `<script>`/`<img onerror>`/`- <script>`). Change is global to all three `mdToHtml` consumers (description, done/delivered detail, question text); the question-text container switched `<span>` → `<div class="q-text">` so emitting block tags inside it is valid HTML. New `<hN>`/`<ul>`/`<ol>` CSS is shared across `.desc-rendered`/`.done-detail-text`/`.q-text`, sized down for compact cards. Webview-render-only: no parser/writer/store/grammar changes (board.js isn't in the Docker unit set — safety net is the fixpoint fixtures staying green + manual F5).
- Delivered/Feedback/Note now render as markdown (t-7a94), matching Description: routed all three through the existing hand-rolled `mdToHtml` renderer (`media/board.js`) plus its `a[data-mdlink]` -> `openLink` wiring — Review-card Delivered (dropped the inline-style plain text node for the `.done-detail-text` markdown-CSS class, matching its DONE-archive sibling), DONE-archive Delivered (same one-line fix its neighbouring Description already had), Review feedback, and the Note chip (both keep their leading warning/clock codicon, only the text body is rendered). No renderer change — `mdToHtml` already escapes all text first, so the only practical effect for these short human/worker-authored fields is that staged-attachment `[label](.loopboard/cache/...)` links become clickable and any `` `code` ``/`**bold**`/bare URLs the author typed render formatted, instead of literal. Answers (edit-only textarea) and unparsed lines (verbatim by design) stay out of scope.
- Attachments broadened to any file type, size-capped only (t-058e): removed the host allowlist (`ALLOWED_ATTACHMENT_EXT`, `store.ts`) and the webview image/-MIME pre-filters (drop + paste, all four surfaces) — `readImageFile` renamed `readAttachmentFile`, no longer rejects non-image `File`s; the size cap (`loopBoard.maxAttachmentSizeMB`, unchanged default 10MB) is now the ONLY gate, host-side in `stageAttachment`. No denylist for executables — explicit human decision, overriding the original story text (\"block binaries\"). Wired `wireFieldAttach` (drop + paste) onto the two remaining unwired surfaces, Review feedback and the note-to-worker field, matching the existing description/answer wiring; `controller.ts`'s attach-message field allowlist extended to admit `feedback`/`note` (previously silently fell through to whole-card Description append). Filename sanitization/traversal guards and the size cap are unchanged; no grammar or fixpoint change (links reuse existing description-link rendering).
- Notes-to-worker reskinned to the qa-* visual idiom (t-b149): `renderNote` (`media/board.js`) now emits a `.qa-note` card (yellow left rail, mono uppercase "NOTE" label, edit/delete link actions), a focus-bordered `.qa-note-composer` (+Attach button, "⌘V pastes screenshots · ⌘↵ saves" hint) for the open/editing state, and a dashed `.qa-note-empty` drop-zone for empty — same visual language as t-2394's Q&A panel, all colors/fonts via `var(--vscode-*)`. Scope stays the smallest reskin (human decision): still ONE ephemeral note (`sendPatch('note', …)`, apply-then-delete, Rule 16), no multi-note model, no per-note attachment storage, no index grammar change — attachment chips are derived by scanning the note text for `[name](.loopboard/cache/…)` links (same `extractAttachments` helper the card-level attachments area uses), not a new data model. "Edit" reopens the composer prefilled with the current note text (an update, not a separate mode); unlike the description/answer fields, pasting/dropping into the note composer stages the attachment and inserts its link WITHOUT auto-committing, so more text or attachments can follow before an explicit Save — the New Story composer's pending-attachment pattern, not the field-attach pattern. Wired the note-scoped attach plumbing (human decision, reuse `wireFieldAttach`): `src/controller.ts`'s attach-message field allowlist now admits `'note'`; `src/store.ts`'s `removeAttachment` now also strips a matching link out of `notes[]` (previously only title/description), so the attachment chip's × actually clears the note's link, not just the cached file. `wireFieldAttach` now returns its internal `stage` function so a drop on the empty-state drop-zone (which has no textarea yet) can still stage a file once the composer opens. No thumbnail previews — a real image preview needs a webview-safe URI for an already-staged file (`asWebviewUri` via a new host round-trip), out of scope for this reskin; every attachment renders as a name chip with an extension badge.
- In-tab filter persists across phase tabs and reloads (t-2452): `searchQuery` (`media/board.js`) is now seeded from `vscode.getState()` on load and included in `saveState()`'s persisted blob (same one `phase`/`collapsed`/composer-draft state already uses), and the plain phase-tab `onclick` no longer calls `resetSearch()` — only genuinely new contexts (opening/closing the New Story composer, `revealTask` jumping to a specific task without an explicit search) still clear it, since an old query could otherwise hide the very task being revealed. One shared query across all tabs (human decision — matches the pre-existing single global `searchQuery`, not per-tab state); the `is:unanswered` token persists the same way since it's just part of the query string. The search input's `input` handler now also calls `saveState()` on every keystroke so a mid-typing reload doesn't drop the in-progress filter.
- t-2452 follow-up: the sidebar's phase-count and attention rows (`media/sidebar.js`) post `{type:'reveal', phase}` with no `taskId` and no `search` for a bare phase-only navigation — `revealTask` (`media/board.js`) was still calling `resetSearch()` on that path (its `else` branch fired whenever `search` was absent, regardless of whether a specific task was actually being revealed), silently clearing the filter every time the user switched phases from the sidebar instead of the in-app tab strip. This was the actual remaining persistence gap the human's second and third feedback reports were hitting (an independent Opus subagent review traced it after a concurrent Opus re-groom pass on the task file had instead concluded the PR was simply unmerged — both were partially right: the PR being unmerged also blocked the first fix from reaching any build, and this second, distinct bug was still there underneath). Fix: only call `resetSearch()` when `taskId` is present (a genuine jump to one specific task, e.g. a disk-wins conflict toast's "Review" action) — a bare phase-only reveal now leaves the filter untouched, matching the in-app tab strip's behavior.
- Attachment chip idiom unified across every surface (t-f51c): `noteAttachmentChip` generalized into a shared `attachmentChip(item, onRemove, clickable)` (`media/board.js`) — description/draft cards' `renderAttachmentsArea`, the new-story composer's pending list, and notes all render through it now, so `.qa-attachment*` is the single chip look/CSS everywhere (deleted the old ad-hoc inline-styled description/composer lists). `clickable === false` (composer's pending list only, no cache file yet) renders a static `.qa-attachment-name.is-pending` name instead of an `openLink` anchor. Answer and feedback — whose attachment links live inline in the field's own free text rather than a separate store — get a parallel `renderFieldAttachmentsArea(text, commit)` that extracts the same links and, on chip removal, strips the link out of that text and re-commits through the field's normal patch path (`sendPatch`), mirroring the note's edit-and-resave pattern rather than a `detach` host round-trip. Behavioural parity (human decision, not just visual): the note composer's `＋ Attach` file-picker button + `⌘V pastes screenshots` hint were added to the new-story composer, description edits, answer edits, and the Review feedback composer — all four already supported silent drag-drop/paste (t-058e/t-att1); this only makes attaching discoverable without a keybinding, same as before, no new host round-trip. Real image thumbnails stayed explicitly out of scope (confirmed unchanged from t-b149's decision).
- New Story composer gains a save keyboard shortcut (t-9b50): the composer `area` textarea now binds a `keydown` listener wiring `isSaveShortcut` (Cmd/Ctrl+S, the existing convention every other editable field already uses) to `commitDraft()`. No new validity check needed — `commitDraft` already no-ops on an empty/whitespace-only composer, so the shortcut is silently inert exactly like the disabled Save Draft button. Scope stayed composer-only (per-card fields already have their own Cmd/Ctrl+S bindings). Review feedback reversed the initial "both Cmd/Ctrl+S and Cmd/Ctrl+Enter" answer — the human called the Cmd/Ctrl+Enter half a mistake on their own accepted answer and asked for Cmd/Ctrl+S only, so the Enter branch was removed.
- Depends-on chips filter instead of jump, for every target (t-a524): added a reserved `task:<id>` token to `matchesQuery` (`media/board.js`, exact case-insensitive id match, ANDs with other tokens like `is:unanswered`). The depends-on chip's `onclick` now routes through `revealTask(dep.id, phase, false, 'task:' + dep.id)` instead of jumping/scrolling, for BOTH Done and active targets — human decision widened the original Done-only scope ("Make it consistent. Do it for ALL stories in all Phases"). A `dep.met` (Done) target skips the `board.phases` existence scan entirely and routes straight to the Done tab, since `dep.met` already reflects `doneIds.has(id)` (`src/view.ts`) independent of the truncated 50-entry `phases.done` window — so an old Done dependency outside that window still resolves correctly instead of a false "not found". A non-Done target still scans `board.phases` for its live phase (unchanged "not found" toast if absent anywhere). Chip tooltip/aria-label changed from "Go to <id>" to "Filter to <id>" to match the new universal behavior.
- Composer attachment size cap enforced at attach time (t-5f50): `WebBoard.maxAttachmentSizeMB` (`src/view.ts`, set in `controller.ts`'s `buildWebBoard`) surfaces the configured cap to the webview so the New Story composer's `addPendingAttachment` (`media/board.js`) can reject an oversized file against `file.size` BEFORE staging it — same "Attachment is too large (max NMB)." message as every existing-card surface, no pending-list entry, no `loopboard-pending:<n>` placeholder inserted. Previously the composer only round-tripped bytes to the host at Save Draft, so the cap silently didn't apply until then. Defense in depth: `store.resolvePendingLinks` (`src/store.ts`) now also takes a `removedTokens` list and strips those placeholders' links entirely (rather than leaving them unresolved) when `controller.ts`'s `createDraftWithAttach` collects a rejected attachment's token — closing a pre-existing gap (independent of this fix) where a save-time rejection always left a dangling `loopboard-pending` link in the new draft. No pure unit test: the boundary lives entirely in `store.ts` (vscode-touching) and `media/board.js` (webview JS), neither in the Docker pure-module set, same as every other `stageAttachment`/`resolvePendingLinks` call site.
- Note-to-worker collapsed-button drop affordance removed + auto-focus on open (t-5b29): the empty-state button's label dropped its `· or drop files here` suffix (now just `＋ Note to worker`) and its `dragover`/`dragleave`/`drop` listeners plus the `u.pendingNoteFile` staging path were deleted outright — the reporter found the collapsed-button drop flow non-functional/not useful, and paste + the composer's own `＋ Attach` button already cover attaching once it's open, so nothing was lost. Also removed the now-orphaned `.qa-note-empty.drag-over` CSS rule. Opening the composer (via the empty button or the "edit" link) now sets a one-shot `u.noteNeedsFocus` flag consumed on the note textarea's next render with `requestAnimationFrame(() => ta.focus())`, mirroring `descNeedsFocus`/`composerNeedsFocus` — one click now both opens the composer and lands the caret, and a background refresh repaint never steals focus since the flag is cleared the instant it's read.
- Phase navigation always clears the in-tab filter; only a custom view (sidebar attention row, depends-on chip) sets one (t-3d42, supersedes both t-2452 decisions above): the board tab strip's `onclick` (`media/board.js`) now calls `resetSearch()` before `saveState()`/`render()`, and `revealTask` (`media/board.js`) drops the `taskId` gate entirely — an explicit `search` argument installs that query, otherwise it always resets, regardless of whether a specific task is being jumped to. This reverses t-2452's "switching tabs no longer clears the filter" behavior, because the two-list sidebar (custom-view attention rows vs. plain PHASES navigation) makes the persisted filter leak into tabs the user never queried, showing a false "No matches" empty state. `vscode.setState` persistence of `searchQuery` across reloads (t-2452's other half) is unchanged — persistence answers "webview was hidden/recreated with no navigation," clearing answers "the user just clicked a phase tab," and the two events don't collide. New reserved token `is:proposal` (`matchesQuery`, `media/board.js`) keeps only non-draft New tasks; the sidebar's "N proposals to approve" row (`media/sidebar.js`) now sends `search: 'is:proposal'` so its tab shows exactly the count in the row, mirroring t-1cdb's `is:draft`/"N drafts will be groomed" row. The search bar (`renderSearchBar`, `media/board.js`) gained a `×` clear button (reusing `.icon-btn` styling) shown only while a query is active — no chip names the active view; the query text itself is the label.
- Board filter is TWO LAYERS: the human's typed filter survives phase navigation, a custom view's query does not (t-1cdb, amends the t-3d42 entry above — an amendment, not a third reversal). t-2452 made one global `searchQuery` survive tab clicks; t-3d42 made it always clear on tab clicks. Neither works alone, because "clear" means two different things depending on where the query came from. `media/board.js` now holds `userQuery` (what the human typed) and `viewQuery` (`null` = no view; a string, INCLUDING `''`, = a view installed by a sidebar attention row or the depends-on chip), plus exactly ONE derived accessor `effectiveQuery()` = `viewQuery === null ? userQuery : viewQuery`. Every read site (`matchesQuery`, `filterList`, `openSearch`, `renderSearchBar`'s input value / match counter / `×` visibility, both "No matches in this tab" empty states) goes through it, so the layering exists in one expression and no consumer learns about layers. Write rules: typing in the search input sets `userQuery` and drops the view (the box is directly editable, so its text is the human's the moment they edit it); `revealTask` with an explicit `search` sets `viewQuery` only, leaving `userQuery` intact underneath — that is what restores the typed filter when the user later clicks a phase tab; phase navigation (tab strip, sidebar PHASES rows, a `search`-less reveal with no `taskId`) calls the new `clearView()`, dropping the view only; `resetSearch()` keeps meaning "clear both" and now serves the New Story composer's open/close, the `×` button, and a task-targeted reveal with no query of its own (revealing a task the board would then hide is the t-2452 failure mode). Both layers are persisted in the same `vscode.setState` blob, preserving t-3d42's reload criterion verbatim. The "N tasks awaiting review" row (`media/sidebar.js`) now sends `search: ''` — an EXPLICIT EMPTY VIEW, distinguished from absent by a `search != null` test in `revealTask` — so a row advertising a count opens a tab showing exactly those N cards, the same parity rule `is:proposal`/`is:draft` already follow. `src/controller.ts` is unchanged behaviourally (it already forwarded `search` verbatim and `''` survives the JSON round-trip); it gained a comment recording that absence is now meaningful. t-3d42's acceptance criterion "a query the user TYPED is cleared by a phase-tab click just the same as one installed by an attention row" is the one thing REVERSED; all its other criteria still hold. No pure module, reserved token, message shape or grammar change — webview-only, so no new unit test; verified through manual F5 (VERIFICATION.md item 14, rewritten a third time).
- Search typing is debounced, not optimised (t-1cdb feedback: "when I type in the search bar it lags. Seems the more text it needs to search the worse it gets."): the search input's `input` handler (`media/board.js`) called `saveState()` + `render()` on EVERY keystroke, and there is no cheap repaint on this board — `render()` wipes `#root` and rebuilds the topbar and every matching card, re-rendering markdown through `mdToHtml`, re-measuring textareas under `requestAnimationFrame`, and restoring focus + caret across two more rAFs. At ~27 New cards that is tens of milliseconds of synchronous work per character, so the input visibly trails a normal typing speed. Fix: assign `userQuery` synchronously (so `effectiveQuery()` is correct the instant anything reads it, and the native input never fights the DOM for the text) but coalesce the repaint — one `setTimeout` at `SEARCH_REPAINT_DELAY_MS` = 120ms, cleared and re-armed per keystroke, carrying `saveState()` with it since persisting an in-progress filter matters for a reload, not per character. Deliberately NOT a `matchesQuery` optimisation (lowercase caches, precomputed haystacks): the filter itself is a substring scan over ~27 short strings and is not the cost; the repaint is. Two ordering details make it safe: `render()` calls `cancelSearchRepaint()` FIRST, before `textContent = ''`, because wiping the DOM blurs the focused search box — without that the new blur handler would re-enter `render()` mid-repaint; and the blur handler exists at all so a pending repaint can never outlive the field it was scheduled for (click a tab or a card field mid-burst and the filter still commits). The alternative — re-rendering only the card list instead of the whole document — was rejected as a much larger change to `renderPane` for a latency problem a 120ms coalesce already removes.
- Promote guard became two cases; a "re-groom pending" badge makes the second visible before you reach for Promote (t-6936). `confirmPromote` (`src/controller.ts`) previously returned `true` the instant no answer was blank, so a New story whose answers were all FILLED but whose `question:`/`answer:` pairs were still present promoted silently — and LOOP.md Rule 14 defines exactly that state as "the groomer has not folded these answers into `## Description` yet". That is the more deceptive case of the two, because the card looks finished: full meter, "N / N answered". It now shows a distinct modal ("These answers haven't been folded into the story yet — promote anyway?") with `detail` explaining what the groomer still owes, while a blank answer keeps t-oqg1's original copy byte-identical and a story with no questions at all still promotes with zero friction. One guard with two branches, not a separate gate action (human decision); `debugLog('info', 'popup-choice', …)` now tags which case fired (`unanswered` vs `regroom-pending`) so the two are distinguishable in `.loopboard/debug.log`. The webview's optimistic-fade predicate (`commitPromote`, `media/board.js`) widened in lockstep from "some question unanswered" to "any question at all" — it exists to avoid greying a card that is about to sit behind a modal, so it must mirror whatever `confirmPromote` decides to prompt on; the two are now commented as a pair. The card-side signal is an additive `.qa-pending` badge in `renderQuestions`'s header BESIDE the existing count rather than replacing it (human decision — the count stays useful and nothing t-2394 built is regressed), driven from the existing `updateHead()` so it flips the moment the last answer is saved without a board refresh. New cards only: a fully-answered Feedback card means the worker resumes, which is correct and pending nothing. No pure helper was extracted for the predicate — the host is TS and the webview is vanilla JS with no shared module, so a `src/view.ts` export would have had no second consumer. No grammar, Rule 14, or Automation-block change: "answered but still present" is fully derivable from the existing `WebTask.questions[].answered` flag.
- Composer commits echo the saved value into the local board snapshot before repainting (t-ff54): every field patch is fire-and-forget, so the `render()` right after a commit still read the PRE-save `board` object and painted the OLD value — the reported "only half of it" (previous, shorter note) and "＋ Note to worker" still showing after a successful add. The confirming refresh does arrive promptly (`onPatch` ends in `refresh()`, plus the debounced watcher notify), but `pendingBoard` parks any incoming board while a field is focused, so with focus anywhere (the click-outside commit puts it in the field just clicked) the stale text stays painted until the next focusout. New `commitPatch(taskId, field, value, base, target, key, questionIndex)` (`media/board.js`, next to `sendPatch`) writes `target[key] = value` on the live board object the renderer reads, then sends the patch; applied at all four composer commit sites (`commitDesc` → `t.description`, `commitAnswer` → `q.answer`, `commitFeedback` → `t.feedback`, `commitNote` → `t.note`) plus the note **delete** button (`t.note = ''`). Deliberately an ECHO, not a flush: the `pendingBoard` focused-field deferral is untouched, and the confirming board still reconciles — on a same-field conflict disk wins exactly as before, the conflict toast plus the refreshed board replacing the echo. The feedback commit and the note delete gained a `render()` call (they previously relied on the confirming refresh to paint the amber block / drop the note card), matching what `commitDesc`/`commitNote` already do; `commitAnswer` still does NOT render — its targeted in-place update exists precisely to protect the focused textarea (t-2b96) — but the echo makes its `q.answer` comparisons (Save-disabled state, Escape-to-revert) correct after a save. Webview-only, outside the Docker pure-module set, so no unit test: manual VERIFICATION.md item 28.
- Answers are HELD on the board until the story is fully answered, then written as ONE patch (t-5e6d): a groomed story's decisions are only complete as a set — Rule 14's re-groom and Rule 10's Feedback resume both want every answer — yet each per-question Save was its own index write, `rev:` bump and nudge, so a 1/3-answered story kept reaching the groomer half-finished. The first cut was doc-only (fix the Rule 14 / Automation "any filled `answer:`" wording, which stays in scope as the second half); the human chose to fix the write path too. A save on a story that still has a blank question now moves the value into `heldAnswers` in the webview instead of posting a patch; the moment the LAST blank question is filled (by a Save, ⌘S, a suggestion Accept, or Save All), the whole set flushes as a single `answers` field patch. No extra button and no new gesture — holding the last one IS the flush trigger — and editing an answer later, when nothing is blank, still writes immediately. `answers` is a new INDEX field in `src/merge.ts` (positional, newline-joined, one line per question, the idiom `note:`/`feedback:` already use), so CLAUDE.md non-negotiable 4 holds unchanged: one field patch, one file, one re-read/re-parse/serialize/atomic write, one `rev:` bump, one nudge with reason `regroom`. Its base is the on-disk answer set, so the existing disk-wins conflict path covers a loop or hand edit landing mid-hold; `applyPatch` additionally rejects a value whose LINE COUNT no longer matches the entry's questions, because a positional apply after a re-groom added or removed a question would silently attach answers to the wrong questions. Held answers live ONLY in the `vscode.setState` blob beside the composer text (human decision): they survive panel hide/reveal and a webview reload, and die with the window — nothing is staged on the host or on disk, so no new file, no `workspaceState`, no cleanup path. They are reconciled on every incoming board (`pruneHeldAnswers`): a held answer survives only while its task still exists, is still New/Feedback, and its question still has the same TEXT and a blank on-disk answer — which means a landed answer prunes itself, a re-groomed question drops its held answer with a toast naming the story, and a CONFLICTED flush keeps everything held and re-savable (the disk answers are still blank). That self-pruning is also why the flush does not clear the held map itself. Batching applies to Feedback cards as well as New (human decision) — they share `renderQuestions`, and Rule 10 already made a 2/3 index state useless there; only the tooltip copy differs. A held row is never disguised as saved: the count/meter treat held answers as given (that is the human's progress), but the rail turns amber and the row carries a `held` tag, and while anything is blank the "N / M answered" count and meter carry a tooltip saying the board is holding the saved answers until all are filled. The t-oqg1 promote guard is deliberately untouched: it reads disk, so promoting a story with held answers still warns about unanswered questions.
- Corrections to the batched-answer design after review of PR #142 (t-5e6d): (a) the prune rule keyed on `!q.answered`, which deleted a held EDIT to a question that was already answered on disk — the test is now "the on-disk answer still differs from the held text", which prunes a landed answer, keeps a conflicted one, and keeps an edit over an existing answer; (b) clearing an answer to blank could never be written at all (a blank keeps the set incomplete, so no flush carries it, and the prune then restored the old value), so a RETRACTION now keeps the old single-question `answer` patch and writes straight through — holding is for incomplete sets, not for undoing a decision the index already records; (c) Save All fanned out per-row commits, each testing completeness against its neighbours' UNSAVED drafts, so a fully answered card flushed on the first row (writing the others at stale values) and again on the next — the row commit is split into `stageRow()` (hold + local echo, no decision) and one `maybeFlush()` taken for the whole card, which Save All calls once after staging every dirty row; (d) the patch value is positional, so a newline inside an answer inflated the line count and the host rejected EVERY flush with a misleading "changed on disk" toast — newlines are folded to spaces at the join (answers are single-line by the index grammar) and the same folded values are echoed locally, with merge.ts's line-count guard kept as the backstop; (e) when the flushed value equals what is already on disk no patch is posted, so no confirming board arrives and nothing pruned the held entries — that case now clears them itself, instead of leaving the row wearing a `held` tag forever.
- Card Description and Open questions fold independently (t-aee3), on a third state map beside the two the card collapse already uses: `sections[phaseKey][taskId] = { description?, questions? }` in the same `vscode.setState` blob, so section state is per tab and survives hide/reveal and a window reload like card state does. A section with NO override falls back to `collapsedDefault[phaseKey]` rather than to "expanded" — that fallback is the whole mechanism behind "Collapse all folds the sub-sections too": `setPhaseCollapsed` wipes `sections[phase]` exactly as it wipes `collapsed[phase]`, so every card in the tab, including ones the user expands by hand afterwards, shows both sections in the button's state, while the per-card chevron keeps toggling only the card. New key, so no migration; unrecognized value means "no overrides". `renderDescription` gained a header (chevron + `Description` label) that renders in BOTH states — collapsed it also carries a one-line ellipsised preview of the first non-empty description line with markdown markers stripped, built by `descPreview()` and inserted as TEXT, never HTML: a preview is not a second markdown surface and must not be able to inject markup. The chevron sits inside `.desc-wrap`, so t-471a's click-outside commit never fires for it and collapsing an open editor has to commit explicitly — `commitDesc` is split into `commitOpenEditor()` (commit, no repaint) plus the rendering wrapper, and the chevron calls the former so `toggleSection`'s own `render()` is the only repaint. - READING and REMOVING a setting are different code paths in VSCode, and only reading is value-tree shaped — the insight the "Migrate Config" button rests on, established from the VSCode source rather than assumed (t-sgrp follow-up). A READ resolves through `toValuesTree`, which logs `Ignoring loopBoard.delegateWork.review as loopBoard.delegateWork is true` and DROPS a child of a scalar, so that key is unreadable through any extension API while its parent has a value — `get`, `has` and `inspect` all resolve out of `contents`, and the unfiltered flat `ConfigurationModel.keys` that would show it is never exposed to an extension. A REMOVE never touches that tree: `update(key, undefined, Global)` runs `ExtHostConfiguration.update` -> `$removeConfigurationOption` -> `WorkspaceService.updateValue` (with an explicit target, so the `inspect`-based short-circuit at the top of it is skipped) -> `ConfigurationEditingService`, whose `getEdits` calls `setProperty(modelContent, jsonPath, undefined, …)` — a JSON TEXT edit computed off `parseTree(text)` of `settings.json` itself. Three facts follow, each load-bearing. (1) The edit finds a property the value tree never exposed, because it reads the file, not the model. Reading or writing `settings.json` behind VSCode's back was never needed and is not done anywhere.
