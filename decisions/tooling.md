# Decisions — Toolchain, CI & packaging

One line each: what, why. Newest at the bottom. Index: [../DECISIONS.md](../DECISIONS.md).

- Tests are plain CommonJS `.js` under `test/`, requiring compiled modules from `out-test/` — keeps devDependencies to `typescript` + `@types/vscode` only (no `@types/node`), per the non-negotiable.
- `tsconfig.test.json` compiles only the pure modules (parser/writer/model/merge) with `types: []` so they never depend on node/vscode typings; the vscode-touching modules are built by the main `tsconfig.json` into `out/`.
- `make test` runs `node --test 'test/*.test.js'` (glob, not a bare dir) because Node 22 treats a bare `test/` argument as a module path.
- Main `tsconfig.json` adds the `DOM` lib (not `@types/node`) to get `setTimeout`/`TextDecoder`/`TextEncoder` in the extension host without violating the "typescript + @types/vscode only" devDependency rule.
- Added `.vscodeignore` so the packaged `.vsix` ships only `out/` + `media/` + manifest/README (26 files) — source, tests, docs, and the design bundle are excluded.
- Release pipeline (t-9c4e) ports ClockClock's semantic-release setup: `.releaserc.json` with the commit-analyzer/release-notes-generator/github plugin trio, `release.yml` with a `release` job (cycjimmy/semantic-release-action@v4, GITHUB_TOKEN) and a gated `vsix` job that builds (npm ci + tsc + node --test on Node 22 — CI runners aren't the host, so the Docker-only rule doesn't apply) and packages with `vsce package <version> --no-dependencies --no-git-tag-version --no-update-package-json` — version is injected into the vsix manifest only; package.json's version stays frozen in git (no bot bump commits). Artifact goes to the GitHub Release via `gh release upload`; Marketplace publish deliberately deferred (t-a37f follow-up). `environment: All` omitted (ClockClock-specific). `.github/**` + `.releaserc.json` added to `.vscodeignore` (they leaked into the vsix, 30→32 files).
- `release.yml`'s push trigger carries a `paths:` allowlist of shipped content only (t-e1d7) — a housekeeping push (`.claude/`, `CLAUDE.md`, `test/`, `decisions/`) starts no run at all, so no tag, no GitHub release and no publish. Deliberately a path allowlist, never a file-extension rule: `media/template-*.md` are markdown AND shipped (every workspace re-syncs its LOOP.md from them) and `README.md` is the Marketplace listing body, so build.yml's `paths-ignore: ['**/*.md']` would have been wrong here. A blocked push is only deferred — it releases with the next push that touches shipped content.
- `.releaserc.json` pins `docs`/`chore`/`ci`/`build`/`test`/`style`/`refactor` to `release: false` via explicit `releaseRules` (t-e1d7) — documentation of the mapping, not a second gate: the default preset has no rules for those types either, so they already produced no release, and commit-analyzer sees commit metadata but never changed files, so it cannot catch the mistyped `feat(docs):` that cut v2.53.0 off a zero-shipped-byte commit. The trigger filter is the real gate. Custom `releaseRules` REPLACE the default preset rather than extend it (commit-analyzer only falls back when they return `undefined`, and a `{type, release: false}` rule matches a breaking commit too and returns `false`), so the block must restate `{breaking: true, release: major}` and `{revert: true, release: patch}` or breaking changes stop releasing entirely — pinned in `test/packaging.test.js`.
- `.vscodeignore` is an allowlist (`**` + one negation per shipped file) rather than a denylist (t-e1d7): a new top-level file can no longer leak in, and packaging dropped from 49 to 39 files (`FAQ.md`, `language.md`, the six `decisions/*.md`, and `media/loopboard-activitybar.svg`, which nothing references — `package-lock.json` and `.vscodeignore` were never packaged, vsce's built-in `defaultIgnore` already excludes them). The inversion's risk — a broad pattern silently dropping a file the extension reads at runtime — is covered by `scripts/assert-vsix-contents.sh`, a positive `vsce ls` assertion that derives the compiled-module list from `src/*.ts` (the entry point alone would not catch a narrowed `!out/**/*.js`), run by `make package` and by both workflows before any upload, plus `test/packaging.test.js` in the Docker suite.
- Marketplace publish is automated as the LAST step of release.yml's `vsix` job (`vsce publish --packagePath` with the repo-level VSCE_PAT) rather than a `release`-event workflow — GITHUB_TOKEN-created releases don't trigger other workflows. It runs after the asset upload and version-bump commit so a Marketplace flake can't block them; `publish.yml` (workflow_dispatch) stays as the manual retry path.
- Marketplace publish moved out of the `vsix` job into its own gated `publish` job (`needs: [release, vsix]`, same `published == 'true'` gate) so GitHub's **Re-run failed jobs** retries only the flaky step (t-9c3d) — v3.5.0 died on a gallery timeout and the human's re-run of `vsix` then failed *earlier*, on the already-uploaded asset, never reaching the publish. Being last protected the earlier steps but made the one genuinely flaky step the one that couldn't be rerun. The new job's only side effect is the Marketplace push, and it publishes the `.vsix` downloaded from the release rather than a rebuild, so it's idempotent and identical to `publish.yml`'s escape hatch. `vsix` itself is now re-runnable too: `gh release upload --clobber`, and the version bump guarded by `git diff --quiet --cached` (a re-run checks out the original triggering SHA, so the commit succeeds and the push is then rejected non-fast-forward against a moved main). Retry is a three-attempt bash loop bounded by `timeout-minutes: 20`, not a third-party action — `vsce publish` has no retry or timeout flag. `--skip-duplicate` replaces the hand-rolled gallery pre-check that was originally specced: it covers both the version-exists query and the 409 from the write, so the Marketplace's ~5-minute index lag can't produce the false negative a read-only pre-check would. `--pat` dropped everywhere in favour of `VSCE_PAT` via `env:`. Pinned in `test/packaging.test.js`.
- All eight `uses:` lines bumped off the Node-20 runtime (t-9c3d): `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`, `cycjimmy/semantic-release-action@v5`. Majors chosen by reading `runs.using` at each tag, not by incrementing — `upload-artifact@v5` is still `node20` despite the release notes' "preliminary Node 24 support", so v6 was its first real node24 major. `semantic-release-action` deliberately stops at **v5** (first node24 major, otherwise a no-op) rather than v6, whose breaking change is `semantic-release` 24 → 25 — a major bump of the tool that cuts our releases, untestable without cutting one, and a separate decision. No `with:` changes were needed: `setup-node@v5`'s auto-cache keys off a `packageManager` field we don't have, `checkout@v6`'s move of persisted credentials to `$RUNNER_TEMP` keeps `git push origin HEAD:main` working, and `checkout@v7`'s fork-PR block needs a `pull_request_target`/`workflow_run` trigger none of the three workflows use. Kept on floating major tags, not SHAs — a version sweep, not a supply-chain-pinning change.
- `contributes.configuration` is four titled sections (t-sgrp): *Models & Slots*, *Agent Setup*, *Board & Workspace*, *Beta (experimental)*, replacing t-set1's two, whose second was a 13-key grab-bag with jumbled orders. Orders are renumbered in TENS within each section so a later insert needs no renumber (asserted, along with per-section uniqueness, in `test/manifest-settings.test.js`). `effort` and `groomConcurrency` deliberately stay under `models.<slot>.*` rather than moving to Agent Setup: the grid owns how they are presented, so the manifest section now only governs the native escape hatch, where mirroring the key namespace is least surprising. The two deprecated keys sit at 900/910 in Agent Setup — out of the tens run, hidden by VSCode anyway, and drawn by LoopBoard's own page not at all.
- A Beta section marks experimental features THREE ways (t-sgrp): the section title, a leading `**Beta —**` sentence in each `markdownDescription` saying the feature may change or be withdrawn, and `tags: ["experimental"]` so the native `@tag:` view agrees. The keys KEEP their ids — no `loopBoard.beta.*` namespace: a rename drops existing values silently, the `application` scope change already costs users their workspace values in the same release (one silent loss per release is enough), and graduating would force a second rename. The section carries the status, not the id. (`@tag:experimental` picking up extension-contributed keys is unverified in a headless session — VERIFICATION.md item 37 asks for it; if it does not, drop the tag and keep the other two markers.)
- Beta graduation rule (t-sgrp): a feature leaves Beta once it has automated coverage or a `VERIFICATION.md` item AND one release cycle with no blocking finding. Graduation moves the key into its real section and drops the Beta marker — it never renames it.
- `test/media-syntax.test.js` parses every `media/*.js` with `new vm.Script(source, {filename})` — compile only, never run, since the webview scripts touch `window`/`acquireVsCodeApi` at load (t-sgrp). `make check` typechecks `src/` and never looks at the vanilla-JS webview scripts, so a syntax error there ships and shows up as a dead panel in the user's editor: `media/markdown.js`'s header comment contained `*italic*/_italic_`, whose `*/` closed the block comment 12 lines early, and since both `board.js` and `settings.js` destructure `window.LoopBoardMarkdown` at load, one comment killed the whole board. The list is read from the directory, not hard-coded, so a webview script added later is covered the day it lands.
- Every `loopBoard.*` property carries `"loopBoardApplies": "live" | "restart"` in `contributes.configuration` (t-sgrp follow-up), saying WHEN a change takes effect: `restart` = frozen into the spawn command (`buildClaudeBase`/`buildLoopCommand` in `src/loop.ts` — permissionMode, loopInterval, the three per-slot `model`/`effort`/`groomConcurrency`, delegateWork, delegateWork.review = 13 of the 27 properties), `live` = read on demand, which is everything else. There is deliberately NO third class: every `getConfiguration` call in `src/` sits inside a closure taken at use time, so nothing is frozen at activation and no setting ever needs a window reload — a classification found to need one is a bug in that closure, not a missing class. The key lives in the manifest rather than in a parallel `src/applies.ts` map because VSCode ignores manifest keys it does not know and `extension.packageJSON` hands back the RAW manifest, so the page reads it with no plumbing and a stale entry for a deleted key is impossible by construction. `test/manifest-settings.test.js` asserts it in both directions — every property has exactly one of the two values, and the `restart` set equals the hand-kept spawn-command list (which is also checked to name only declared keys) — so a setting added without a classification turns the suite red. That guard is what makes the ABSENCE of a marker on the settings page information ("this one is live") rather than an oversight, and it is why `live` rows deliberately get no "applies immediately" chip.
- One standard sentence, `Applies on the next loop start (▶) or restart (♻): a running loop keeps what it was spawned with.`, ends the `markdownDescription` of every `restart` property (t-sgrp follow-up) — the NATIVE settings editor cannot render LoopBoard's marker, so the fact has to ride the description there. It replaces four ad-hoc phrasings ("Frozen into the spawn command…", "A change takes effect the next time…", "…needs a loop start or restart (♻)", "only the mode rides the loop's bootstrap prompt, so…") and is hand-written in the static JSON but test-asserted against the one exported constant (`APPLIES_RESTART_SENTENCE`), including the negative: no `live` description may carry it, nor end on its own ▶/♻ note. `afterTask` and `contextLimit.percent` were reworded in the same pass because their restart PROSE is about restarting loops as a feature, not about the setting landing — "Whatever this is set to, the ♻ button still recycles a loop by hand at any time" and "Automatically restart a loop once its Claude session fills…".
- No `loopBoard.*` property id may be a prefix of another (t-sgrp follow-up), enforced by an exception-free pairwise check in `test/manifest-settings.test.js`. VSCode stores settings as a flat map but resolves them as a TREE, so a key holding a scalar cannot also have children: shipping `loopBoard.delegateWork` (boolean) alongside `loopBoard.delegateWork.review` made VSCode log `Conflict in settings file … Ignoring loopBoard.delegateWork.review as loopBoard.delegateWork is true` and DISCARD the user's value — precisely when the child mattered — after which `c.get('delegateWork.review', true)` silently returned the default. The defect shipped in v3.7.0 (t-e3c3) and was invisible to the manifest, the settings page and `make check`; only the user's VSCode log ever said so. Fix was a rename to the sibling id `loopBoard.delegateReview`, which is NOT a counter-example to the "graduating must never rename a key" rule: the old id had no honoured value to drop. Dotted NAMESPACES stay legal and are unaffected — `loopBoard.contextLimit.percent`/`.action` and `loopBoard.models.<slot>.<field>` have no scalar property above them, which is the whole rule; the guard was checked against both. README carries the migration note (machine-owned settings region regenerated; the note sits outside the sentinels).
- New defaults (t-2047): `loopBoard.contextLimit.percent` `0` → `35` (`contextLimit.action` stays `recycle`), `loopBoard.delegateWork` `false` → `true`, `loopBoard.delegateReview` `true` → `false` — out of the box a loop delegates implementation with no review subagent and recycles at 35% context, never while it owns the In Progress task. Only unset keys change; explicit user values (even `false`/`0`) are kept. The delegation pair GRADUATED from Beta into *Agent Setup* (orders 70/80, after `nudgeLoops`), tags and `**Beta —**` sentence dropped, ids unchanged, because the graduation rule above is met: coverage in `test/loop.test.js` + VERIFICATION item 35, and a release cycle with no blocking finding (t-e3c3 shipped in v3.7.0; current v3.18.0).
- The now-empty *Beta (experimental)* section was DELETED rather than kept as an empty heading (t-2047) — three sections, orders 1–3. The tag-driven rendering (`EXPERIMENTAL_TAG`, `isTaggedBeta`, the section `beta` flag in `src/settingsform.ts`; the heading and `experimental` chip in `media/settings.js`) is KEPT for future betas and stays covered by a synthetic-manifest test in `test/settingsform.test.js`; `test/manifest-settings.test.js` now asserts no Beta section and no `experimental`-tagged key, so a new beta must bring its markers and tests together.
- Only the host `c.get` fallbacks follow the manifest defaults (t-2047): `src/extension.ts` (`delegateWork` → `true`, `delegateReview` → `false`) and `src/controller.ts` (`contextLimit.percent` → `35`), pinned by a source-text test in `test/manifest-settings.test.js` that fails when a fallback and its manifest default disagree (the host modules cannot be imported in Docker). `buildLoopCommand`'s parameter defaults (`delegateWork = false`, `delegateReview = true`) and its non-boolean handling stay as they are — hostile/absent-config safety handling (non-boolean = delegation off), not the user-facing default, which the manifest owns.
- Release visuals (t-7e1a, amends the t-9c4e pipeline and the t-9c3d job split): a step in the `release` job, straight after `Semantic release` and gated on `new_release_published`, appends the showcase GIFs a commit in the range designated with a `Release-Visual: <file>.gif` trailer to the `vX` GitHub Release body, in one marker-guarded (idempotent) section after Features / Bug Fixes, captioned from `docs/showcase/README.md`'s `alt`, pinned to the tag's raw URL. Designation is a per-commit trailer — survives the `COMMIT_MESSAGES` squash and counts only for the release containing it — not a scene flag or README marker, which persist across releases (the marker would also leak into `README.md` via `make readme`). The range comes from the step's own outputs (`last_release_version`..`new_release_version`, verified against semantic-release-action@v5's `action.yml`), so no tag lookup and no job-`outputs:` wiring. Pure builder + thin git/gh wrapper in `scripts/release-visual.js`, required by `test/release-visual.test.js` (no process spawned). Human-accepted trade-off (2026-09-26): the step and its `setup-node` carry `continue-on-error: true` — unguarded, a failure fails `release` and, through `needs: release`'s implicit `success()`, skips `vsix` and `publish` (a tag with no `.vsix`, which "Re-run failed jobs" cannot recover since the re-run finds nothing to release). Guarded, a failure costs only that release's GIF section: it shows red, is never retried automatically (a re-run gates it off) and is fixed by hand, but never blocks `vsix` or `publish`. Unlike t-9c3d's split, it is neither isolated nor re-runnable alone — accepted over a separate job to avoid output wiring.
